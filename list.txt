A1. Creating a department produces an unusable record               [HIGH]
    HospitalSystem/Services/Deparment/DepartmentCreationService.cs:27
    HospitalSystem/Entities/DepartmentEntity.cs:5
    HospitalSystem/Services/Deparment/DoctorDepartmentService.cs:36-37

    The creation service inserts:
        _context.Departments.Add(new DepartmentEntity { Department = dto.Name });
    IsActive is never set. The entity declares it with no initializer:
        public bool IsActive { get; set; }
    so it defaults to false. Assigning a doctor then hits:
        if (!department.IsActive)
            return DepartmentActionResultDto.Fail("This Deparment isnt active");

    Every department created through the API is born disabled and rejects
    doctors. There is no endpoint that activates a department by id other than
    ChangeDepartmentStatus, so this is recoverable but the create flow is
    broken end to end.

    FIX: set IsActive = true in the creation service, or default it on the
         entity. Add a test asserting a freshly created department accepts a
         doctor assignment.

A2. Double-booking race condition                                   [HIGH]
    HospitalSystem/Services/Appointments/AppointmentCreationService.cs:42-59
    HospitalSystem/Services/Appointments/AppointmentCreationService.cs:89-100

    HasOverlapAsync() runs an AnyAsync check, then execution continues to
    _context.Appointments.Add(appointment) and SaveChangesAsync(). Nothing sits
    between them - no transaction, no unique constraint. Two concurrent
    requests for the same doctor and time both pass the check and both insert.

    The index that exists is not unique:
        ApplicationDbContext.cs:57
        builder.HasIndex(a => new { a.DoctorId, a.Status, a.TimeOfAppointment });

    FIX: add a filtered unique index on (DoctorId, TimeOfAppointment) where
         Status = 'Scheduled', then catch DbUpdateException around SaveChanges
         and return a 409. The check stays as the fast path; the constraint
         makes it correct.

A3. Schedule create and modify anchor to different base dates       [HIGH]
    HospitalSystem/Services/Calendar/ScheduleCreationService.cs:33
    HospitalSystem/Services/Calendar/ScheduleModificationService.cs:38

    Creation:     var dummyDate = new DateTime(2000, 1, 1, 0, 0, 0, DateTimeKind.Utc);
    Modification: var baseDate = DateTime.UtcNow.Date;

    Both then do baseDate.AddHours(dto.StartHour) and store the result. So a
    created schedule lives on 2000-01-01 and an edited one lives on today. The
    overlap query compares absolute instants:
        u.EndTime > start && u.StartTime < end
    which silently stops matching once the two anchors diverge. Editing a
    schedule moves it out of the range every other schedule is compared against.

    FIX: store working hours as TimeOnly (or int minutes-from-midnight) rather
         than DateTime. If that is too large a change now, pick one anchor
         constant and use it in both services.

B1. Nothing is logged, anywhere                                     [HIGH]
    HospitalSystem/Program.cs:172-183
    Whole backend

        grep -rn 'ILogger' HospitalSystem --include=*.cs \
          | grep -v /obj/ | grep -v /bin/
        (no output)

    Zero ILogger references in the entire application. The global handler is:

        app.UseExceptionHandler(errorApp => {
            errorApp.Run(async context => {
                context.Response.StatusCode = 500;
                await context.Response.WriteAsJsonAsync(new {
                    error = "Something went wrong while processing the request."
                });
            });
        });

    It never reads IExceptionHandlerFeature, so the exception object is
    discarded before anyone can see it. There are also zero try/catch blocks in
    Controllers, Services, Data, Entities, Dto or Interface - the only throw in
    the project is Program.cs:113.

    Combined with A2, A9 and A13, several *expected* failure modes surface as
    untraceable 500s. Nothing else on this list can be diagnosed in production
    until this is fixed. This is the highest-leverage item in the file.

    FIX: adopt .NET 8 IExceptionHandler + AddProblemDetails(), inject ILogger,
         log the exception with a correlation id, keep the opaque client
         message.

B3. Login is a user-enumeration timing oracle                       [HIGH]
    HospitalSystem/Services/Auth/LoginService.cs:28-36

        var user = await _context.Users.SingleOrDefaultAsync(u => u.Name == dto.Name);
        if (user == null)
            return LoginResultDto.Fail("Invalid credentials");     // returns immediately
        var result = _hasher.VerifyHashedPassword(user, user.PasswordHash, dto.Password);

    When the user does not exist the request returns without hashing. When it
    does, it spends ~100k PBKDF2 iterations. The message is identical but the
    response time is not, so valid usernames are discoverable.

    FIX: always run a verify against a fixed dummy hash when the user is
         missing, then return the same failure.

B4. Rate limiter collapses to one bucket behind a proxy             [HIGH]
    HospitalSystem/Program.cs:146-155

        var clientIp = httpContext.Connection.RemoteIpAddress?.ToString() ?? "unknown";

    There is no UseForwardedHeaders anywhere in the project. Behind the nginx
    container, or Cloudflare, RemoteIpAddress is the proxy for every request -
    so all clients share a single 60/min window. One noisy client denies
    service to everyone, and per-IP limiting provides no protection at all.

    FIX: add UseForwardedHeaders with a configured KnownProxies/KnownNetworks
         list, before the rate limiter.

B5. No separate rate limit on login                                 [HIGH]
    HospitalSystem/Program.cs:146-155
    HospitalSystem/Services/Auth/LoginService.cs:23-41

    The global limiter is 60 requests/minute for everything. /api/Auth/login
    gets the same budget as a read-only listing - 60 password guesses a minute,
    per bucket, and see B4 for how weak that bucket is. There is no account
    lockout, no failed-attempt counter, and login failures are not audited
    (IAuditLogService is not injected into LoginService).

    FIX: add a named, much stricter policy on the login endpoint, plus a
         per-account failed-attempt counter with a lockout window.

B6. No fallback authorization policy                                [HIGH]
    HospitalSystem/Program.cs:191

    Security depends entirely on every controller action remembering its
    [Authorize] attribute. AddAuthorization() is never called explicitly - it
    works only transitively via AddControllers(). A forgotten attribute ships
    an anonymous endpoint with no signal.

    FIX: AddAuthorization(o => o.FallbackPolicy = new AuthorizationPolicyBuilder()
             .RequireAuthenticatedUser().Build());
         then mark the login endpoint [AllowAnonymous].
